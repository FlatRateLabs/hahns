# Project Overview

- **Project name:** H.A.H.N.S — **H**ardware, **A**dvisories, **H**ighlights, & **N**avigation **S**pecialist (mascot "Hahns" — a friendly wrench character; artwork added v0.3.9, masters in `src/assets/`). Formerly code-named "VW Job Buddy".
- **Purpose:** A no-install browser helper that reads the VW repair procedure a technician already has open in ELSA (via vw-now.com → ELSA 2 Go / ELSA Pro) and pulls the job-relevant data into one tidy, printable panel: torque specs, replace-after-removal (one-time-use) parts, fluids & capacities, special tools, critical warnings, and the numbered overview diagram.
- **Target users:** VW dealership technicians at the bay, using locked-down shop computers. Primary stakeholder/owner: a VW tech (GitHub `senditbro`), not a developer — explain changes in plain terms.
- **Core value proposition:** One click collects everything a tech needs for a job (across multiple manual pages), labels each spec with the component callout number so it maps to the diagram, and prints a clean job sheet — **while keeping nothing** (no files saved, no manual content sent anywhere). Ships as a bookmark, so nothing installs on restricted machines.

# Architecture

- **Frontend:** A single self-contained vanilla-JS bookmarklet. No framework, no build-time transpile, **no runtime dependencies**. The UI panel is rendered into a **Shadow DOM** root injected into the host (ELSA) page so ELSA's CSS can't touch it and vice-versa. Written in conservative, broadly-compatible JS (mostly `var`/`function`, try/catch around anything risky).
- **Backend:** None. There is no server-side component. All extraction/rendering happens locally in the browser.
- **Database:** None. Transient state lives in **`sessionStorage`** (per-tab, auto-clears on tab/browser close):
  - `vwjb_job_v1` — the running job (collected specs, tools, diagram URLs, title, **and `__vehicle`** — the loaded vehicle `{vin, year, model, engine, trans}`, v0.3.2+). No separate vehicle key: it rides inside the job so it shares the job's lifecycle (cleared on Exit / New job, survives page-to-page navigation).
  - `vwjb_pos_v1` — remembered panel position.
  - `vwjb_min_v1` — minimized (collapsed) state.
  - `vwjb_vehexp_v1` (v0.3.7+) — green vehicle-bar expand/collapse state (`"1"` expanded, `"0"` collapsed, **absent** = never set → render expanded then auto-collapse after 3 s once per load). Pure UI flag, never job/ELSA content.
  - **Exit** (the panel ✕, with a confirm dialog) clears all four of the above.
  - **`localStorage` key #1**, `vwjb_upd_reminder_v1` (v0.3.0+) — **REMOVED in v0.4.1.** The entire weekly Wednesday update reminder is gone (superseded by the v0.4.0 self-updating loader; the panel "check for latest" link was removed the same release). The key may linger harmlessly in old browsers — nothing reads or writes it now. (History: it was the Wednesday-marker `YYYY-MM-DD` of the last Wednesday the banner showed.)
  - **Shop special-tool list — IndexedDB `hahns_db` `tools` store (v0.3.16+; was `localStorage` key #2 `vwjb_tools_v1` in v0.3.10–v0.3.15).** The **shop's special-tool list** (tool number → drawer/location + any "missing/check" status), uploaded by the tech as a CSV/.xlsx. Shape `{updated, count, file, fmt, map:{NORM:{n:original, d:drawer, s:status}}}`, keyed by `normTool()` (alphanumerics-only, uppercase). As of **v0.3.16** it lives in the **shared `hahns_db` IndexedDB** (the app DB — renamed from `hahns_fluids` in v0.3.16 since it now holds more than fluids; `APP_DB="hahns_db"`, `APP_DB_VER=2` (bumped in v0.4.1), eight stores `pdfs/parsed/meta/kv/tools` + `sx_pdfs/sx_parsed/sx_meta`) as a **single record** (`{k:"shop", data:{…}}`). A **synchronous in-memory cache** (`shopTools`) is hydrated from IDB at boot (`hydrateShopTools`, folded into `fluidsBoot` so the DB opens once), so `loadShopTools()` + every render/match path stay synchronous & unchanged. **`saveShopTools` is async** (`Promise<boolean>`): it updates the cache + invalidates the `toolDict` matcher immediately, then writes IDB (localStorage fallback if IDB is down). **Shop config, not job data** — **NOT** cleared by Exit / New Vehicle / Clear info, only by Settings "Remove list". The shop's own data (never VW/ELSA manual content), read via a **local FileReader (NOT a network call)**; stored in the browser's own DB, **never uploaded** — zero-network posture intact. The old **`vwjb_tools_v1` localStorage key is kept only for one-time migration (`migrateLegacyTools`, kv flag `migratedToolsV1`) + an IDB-unavailable fallback**. Surfaced in the diagnostic dump (tagged `[IndexedDB]`/`[localStorage(fallback)]`). See "Shop special-tool list" under Key functions.
  - **Fluid capacity tables — IndexedDB `hahns_db` (v0.3.15+, was `localStorage` key #3 `vwjb_fluids_v1` in v0.3.13–v0.3.14; DB named `hahns_fluids` in v0.3.15, renamed `hahns_db` in v0.3.16).** IndexedDB is the **primary** fluid store (DB name `hahns_db`, `APP_DB_VER=2` since v0.4.1) with four fluid object stores keyed by model-year string (the DB also has a `tools` store since v0.3.16 + three `sx_*` stores since v0.4.1): **`pdfs`** (the original uploaded PDF as a **Blob** — now KEPT, was discarded pre-v0.3.15 — + hash/size/fileName/importDate), **`parsed`** (the parsed `models` + `parserVersion`/`family`/`parsedDate`), **`meta`** (lightweight index: parserVersion, hash, size, `hasBlob`, `status`, dates, `appBuild`), and **`kv`** (db-level scalars: `migratedV1` flag, `lastBgUpdate` ms). A **synchronous in-memory projection** (`fluidsData`, the same `{updated,count,years:{Y:{models,file}}}` shape the render path always used) is hydrated from `parsed` at boot so `fluidsBar`/`openFluidsWindow`/`debugDump` stay synchronous & unchanged. **Why keep the PDF:** so an improved parser can **auto re-parse** every saved year in the background (no re-upload) — the whole point of v0.3.15. Same shop-config lifecycle (**NOT** cleared by Exit / New Vehicle / Clear info — only by Settings "Remove tables", which clears all IDB stores + the legacy key). Still **local-only, zero network**: PDFs read via **local FileReader**, stored in the browser's own DB, **never uploaded**. The old **`vwjb_fluids_v1` localStorage key is kept only for one-time migration + an IDB-unavailable fallback**. Surfaced in the diagnostic dump + the Settings "Fluid database" info panel. See "Fluid storage v2" under Key functions.
  - **Service Xpress torque — IndexedDB `hahns_db` stores `sx_pdfs`/`sx_parsed`/`sx_meta` (v0.4.1).** Oil drain plug + wheel bolt torque from the yearly **VW Service Xpress** charts (PDF). **Keyed by SOURCE FILE** (`keyPath:"key"` = fileName), NOT by year — because **one chart bundles several model years** (e.g. the 2013 file has 2013+2014 tables; the 2018 file has 2019+2021, no 2018!) and the filename year is NOT authoritative for content. Mirrors the fluid store otherwise: `sx_pdfs` (original PDF Blob kept for auto-reparse), `sx_parsed` (`{key, parserVersion, entries, years, parsedDate}`), `sx_meta` (lightweight index). A sync projection **`sxData`** (`{byYear:{Y:[entry…]}, files, years, count, updated}`) is built at boot (`hydrateSx`, folded into `fluidsBoot`), deduped by `(year|modelNorm|platform)` preferring the entry whose file-name year matches. Own version constant **`SX_PARSER_VER`** (bump → stored charts auto-reparse via `reconcileSx`/`reparseSxFile`). localStorage fallback `vwjb_sx_v1` (projection-only, no Blob) when IDB is down. Same shop-config lifecycle (**NOT** cleared by Exit/New Vehicle/Clear info — only Settings "Remove charts"). Local-only, zero network; source charts never uploaded/committed. Surfaced in the diagnostic dump. See "Service Xpress torque" under Key functions.
  - **History:** the v0.2.x auto-update keys (`vwjb_last_update_check_v1`, `vwjb_last_update_result_v1`, `vwjb_upd_blk_dismiss_v1`) and the v0.1.1 changelog key (`vwjb_seen_ver_v1`) were **removed in v0.3.0** when the network update check and the in-app changelog pop-up were dropped.
- **Hosting / deployment:** Static. Source repo **github.com/FlatRateLabs/hahns** (public). Hosted on **GitHub Pages** from the **`/docs`** folder of `main`. Live setup page (share this with techs): **https://flatratelabs.github.io/hahns/**. Pages auto-redeploys ~1 min after push.
- **Authentication:** None in the tool. It only reads pages the tech has already logged into. (A Google-Authenticator/TOTP auto-fill feature was explored and **shelved** — see Design Decisions / Known Constraints.)
- **Third-party services / APIs:** **The ELSA page itself makes ZERO network calls** — no job/manual content ever leaves, no in-page phone-home (the v0.2.x in-page `fetch` of `version.json` was blocked by ELSA's CSP and removed in v0.3.0; **do not re-add an in-page fetch/XHR/img phone-home**). **v0.4.0 exception (self-updating loader):** at most **once a day**, the loader opens a **separate GitHub Pages popup** that fetches Hahns's own `version.json` (+ `app.js` only when a newer version is accepted) and `postMessage`s it back — see the Architecture "self-updating loader" note + [[self-update-channel-works-on-elsa]]. This is a real, deliberate network use, but it pulls **only Hahns's own code in** and sends **nothing** about the job out, and the request originates from the popup's GitHub origin, not the ELSA document — so the privacy promise (retain nothing / send nothing) holds. The v0.3.0 network-free Wednesday reminder still exists as a fallback nudge. **v0.4.6 exception (feedback relay):** a **user-clicked** GitHub Pages popup (`report.html`) POSTs a tech's typed bug report / feature request to a **Cloudflare Worker** (`worker/report.js`, hosted at `hahns-feedback.rvanpolen89.workers.dev`) which files a **labeled GitHub issue** (`bug`/`enhancement`) via a fine-grained token held **only** in the Worker's secret store. Same posture as the update channel: it originates from the popup's GitHub origin (not ELSA), and it sends **only what the tech types + app version + browser** — **never** any ELSA/job/manual content (not even the diagnostic dump). Gated by the Worker's Origin allowlist (`https://flatratelabs.github.io`) + a soft shared gate-string (`REPORT_GATE` in build.js, matching the Worker's `SHARED_SECRET`). See the `src/report.html` folder-structure entry. `gh` CLI (Homebrew, authed as `senditbro`) manages repo/Pages from the dev machine.

## Key functions in `src/helper.js`
- `gatherSegments(doc)` — walks the live DOM into ordered `{text, bold}` segments; breaks at block boundaries, joins table cells per row, recurses same-origin frames.
- `extractSegments(segments)` / `extract(text)` — the extractor. `SECTIONS` array defines the 5 buckets (`torque`, `replace`, `fluids`, `tools`, `warnings`) with `test()` regex; `torque`+`replace` have `autoPart:true`, `torque`/`replace`/`fluids` have `label:true`.
- **Vehicle init (v0.3.2, gating fixed v0.3.3):** `extractVehicle(segments)` reads ELSA's **Vehicle Summary** page into `{vin, year, model, engine, trans}` (any field may be `""`). **Tuned against a real summary dump (ATLAS, 2026-06):** ELSA lays each field out as a "Vehicle Data" section where the label ("Model Name", "Engine Code", "Model Year", "Trans Type") is its own line and the value is the **next** line. `VEH_LABELS` holds those four labels **anchored to line start**; `vehField(lines, labelRe, valRe)` takes the rest-of-line or next line. VIN uses `VIN_RE` (17 chars, no I/O/Q) + `looksVin`. `VEH_FIELDS` = shared display order; `vehLoaded(r)`=truthy VIN; `vehMissing(v)`=blank labels. **Gate — `isVehicleSummaryPage(segments)`:** a VIN is NOT proof of the summary (ELSA shows the selected VIN in its header on EVERY page — this caused a repair page to load a half-wrong vehicle pre-0.3.3). The gate requires the summary's structure: a "Vehicle Data" header and/or ≥2 of the four anchored labels. **`run().scan()`:** until loaded, a scan only loads when `isVehicleSummaryPage` is true (then VIN required); otherwise blocked with a `vehNotice` ("this isn't the Vehicle Summary page"), nothing collected. Once loaded, scans collect procedure specs as before. The bar renders via `vehicleBar(r)` (green strip, blanks flagged + click-to-edit `.vval`), hidden in `embed` (demo) mode. Vehicle flows into `plainText`/print/`debugDump` (the dump reports `looks like Vehicle Summary: yes/no` + the per-field grab).
- **Fluid capacity tables — local PDF pipeline (v0.3.13, replaced the hosted v0.3.4 lookup):** the `fluids` SECTION stays `linkOnly:true` (not scanned). # Development Standards

- **Coding style:** Vanilla, dependency-free, broadly-compatible JS. Match the existing file: `var`, named `function`s, IIFE module pattern, single shared `window.VWJB` namespace. No frameworks, no bundler. CSS is a single concatenated string constant in `helper.js`; the panel uses short class names inside its shadow root.
- **Naming:** `camelCase` functions/vars; `SCREAMING_CASE`/`PascalCase` module constants (`SECTIONS`, `BUILD`, `VERSION`, `STORE_KEY`, `TRASH`, `IMG_ICON`, `SITE_URL`). sessionStorage keys are `vwjb_*_v1`.
- **Error handling:** Wrap all DOM access, cross-origin frame access, `sessionStorage`, clipboard, and `getComputedStyle` in `try/catch` and **degrade gracefully** — never throw into the host page. Cross-origin iframes silently skipped.
- **Security / privacy (CRITICAL — this is the product's promise):** The **ELSA page itself makes ZERO network calls** — no manual/job content ever leaves, no in-page phone-home, nothing saved to files. **The product promise is "retain nothing / send nothing about the job," and that is intact.** **v0.4.0 exception:** the self-updating loader opens a **separate GitHub Pages popup** (not the ELSA document) at most once a day to pull **Hahns's own code** in — it never reads or sends ELSA/manual content, so it is NOT a privacy regression, but it IS a deliberate, documented reversal of the old "zero network, no exceptions" *architectural* stance; the GitHub account is now a trust anchor for code that runs in ELSA's authenticated session. See [[self-update-channel-works-on-elsa]]. Only the extracted working list + UI state in sessionStorage (volatile), plus `localStorage` shop config (the weekly-reminder date) and **IndexedDB** shop config (`hahns_db` — fluid tables + the original PDFs as Blobs since v0.3.15, **and the shop tool list since v0.3.16**; DB renamed from `hahns_fluids` in v0.3.16) — the shop's own data, never ELSA/manual content, **all local, never uploaded**. Diagrams stored **by URL reference, not copied**. Shadow DOM isolation. **Fluids (v0.3.13, storage reworked v0.3.15):** the lookup window is **built locally** from tables the tech converted on that computer — no hosted page, no hosted data, no URL parameters at all. **The source PDFs are now kept locally in IndexedDB (v0.3.15, previously discarded) so improved parsers re-apply automatically — this is still 100% local (the tech's own file, in the tech's browser) and is NOT a privacy regression: nothing is uploaded, nothing goes to GitHub.** The old v0.3.4 "our-origin window fetches published data" design is GONE, and **no VW fluid data lives in the repo anymore** (source PDFs + review sheets stay gitignored). Flag any change that would send job/ELSA content anywhere, add a runtime network call, or put VW data back in the repo.
- **Performance:** Designed around a single user-initiated "Scan page" click, so per-scan DOM walking + `getComputedStyle` is acceptable. Keep the bookmarklet self-contained (payload ~336 KB as of v0.3.15 — the in-browser PDF reader added ~120 KB in v0.3.13, the IndexedDB fluid store + info panel ~25 KB in v0.3.15; installs and runs fine as a bookmark URL). Note: the fluid **PDFs live in IndexedDB at runtime, NOT in the bookmarklet** — storing PDFs adds nothing to the payload.
- **Verification:** No unit-test framework, but there IS a **parser regression test** (`tools/parser-test.js`, snapshot-diff over all real fluid + SX PDFs — run it after ANY parser change; see Common Commands). Otherwise verify with (a) `node --check src/helper.js` for syntax, (b) a Node eval harness (`global.window={}; eval(helper); window.VWJB...`) for logic, and (c) the browser preview. ALWAYS `node --check` after editing `helper.js` — a stray quote silently breaks `window.VWJB`.

# Design Decisions

- **Bookmarklet, not a browser extension:** shop machines are locked down and can't install extensions; a bookmark needs no install/admin.
- **Local-only extraction, not an LLM:** ELSA content is licensed; "retain nothing / send nothing" is the core promise, so all parsing is on-device pattern matching.
- **Component numbering via ADD-button counting:** the displayed 1./2./3. are CSS list markers absent from page text (discovered via a real-page diagnostic). Each component name follows an "ADD" button, so counting them reproduces ELSA's numbering. Bold is NOT required (the whole legend is bold).
- **`sessionStorage` for multi-page jobs:** survives page-to-page navigation (the panel is destroyed on navigation) yet auto-clears on tab close — matches "retain nothing." Diagrams stored as URLs (not data) to stay lightweight and reference-only.
- **Shadow DOM panel + pointer-capture dragging:** isolation from ELSA CSS; pointer capture keeps drag working over ELSA's iframes.
- **GitHub Pages from `/docs`:** free, public, trivial updates; the version stamp lets techs confirm they re-dragged the latest.
- **Single `VERSION` constant** in `build.js`; user-facing stamp = `v<VERSION> · <UTC date time>`. (alpha/testing stage).
- **Weekly reminder instead of a network auto-update (v0.3.0):** since no over-the-wire check can run on ELSA (CSP), the app can't *know* if it's stale — so it just nudges the tech to go look. Kept deliberately un-annoying: the banner fires **only on Wednesday** (`new Date().getDay() === 3`) and **only once** that day — `reminderDue()` records this Wednesday's marker (`YYYY-MM-DD`) the instant it returns true, so re-opening the panel later the same day won't show it again. The tradeoff (accepted by the owner): a tech who never opens the app on a Wednesday won't see it that week — fine, because it's a soft nudge, not a real alert, and the app may not even be out of date. Pure local date math = no network, works the same inside ELSA.
- **TOTP shelved:** Google Authenticator codes can only be reproduced from the secret seed (no "sign in with Google" path exists); the seed may be admin-locked under Group Retail Portal, and colocating the 2FA factor on the PC weakens security and may violate GRP policy. Parked pending the owner getting the seed + policy clearance.

# Known Constraints

- **Browser support:** Works in **Chrome, Edge, Safari**. **Firefox does NOT work** — it enforces the page's CSP on bookmarklets (others exempt user-clicked bookmarklets). Not fixable without an extension. Verified on multiple machines 2026-06-20.
- **Updates require re-dragging — SUPERSEDED by v0.4.0's self-updating loader.** Historically the bookmark was a frozen snapshot: users hard-refreshed the setup page (Cmd/Ctrl+Shift+R) THEN re-dragged. **As of v0.4.0 the dragged bookmark is a tiny loader that updates itself** (see the two corrected bullets just below + [[self-update-channel-works-on-elsa]]); techs re-drag only for the **one-time switch** to the loader, or if the loader itself ever changes (hosting URL / update protocol / storage keys / throttle). App changes (fluids/tools/etc.) no longer need a re-drag.
- **The bookmark-bar icon can't be customized — SETTLED (confirmed on owner's Chrome, v0.3.9, 2026-06-29):** Chrome takes a bookmark's icon from the favicon of the *web page* it points to; a `javascript:` bookmarklet points to no page, so it always shows the **default globe**. The v0.3.9 Hahns favicon/apple-touch-icon DO apply to the **browser tab** (and the setup/fluids pages), but **not** to the dragged bookmark — current Chrome does not copy a source page's favicon onto a `javascript:` bookmark. The only paths to a custom bookmark icon are a browser extension (ruled out — locked-down shop machines) or manual per-machine editing (not realistic). **Don't re-attempt this from the page side; the globe stays. The bookmark is labeled "H.A.H.N.S" for identification.**
- **A self-updating loader IS possible on ELSA (v0.4.0, 2026-07-09) — the earlier "IMPOSSIBLE" claim was wrong.** ELSA's real CSP (read by a tech 2026-06-25):
  `default-src 'self'; frame-ancestors 'self' elsa2go.vwhub.com; object-src 'self' *.vwhub.com *.accessaudi.com; block-all-mixed-content; style-src 'self' 'unsafe-inline'; script-src 'self' 'unsafe-inline'; frame-src 'self' blob: *.vwhub.com *.accessaudi.com; connect-src 'self' blob:; img-src 'self' blob: data:`.
  What's true: the **in-page** external-code paths ARE all blocked — `script-src` (no external `<script src>`), `connect-src` (no `fetch`/XHR to our domain), `frame-src` (no external iframe). The old conclusion "there is **no** external-code path" was the error. **The open channel (governed by none of those directives):** `window.open()` a GitHub Pages popup (a new browsing context, NOT a subresource load, so not blocked) → the popup fetches freely on its **own** origin → `postMessage`s the code back to `window.opener` (ELSA sets **no COOP** that severs the opener link) → the ELSA page runs it as a **dynamically-created inline `<script>`** (`.textContent` + append), allowed by `script-src 'unsafe-inline'`. **NOT** `eval`/`new Function` — those need `'unsafe-eval'`, which is absent, so they're blocked regardless of calling context. Owner-verified on real ELSA. The classic self-contained bookmarklet still runs and is the **offline fallback the loader caches** (`app.js`). See [[self-update-channel-works-on-elsa]] + the Architecture "self-updating loader" note.
- **In-page network auto-update stays REMOVED (still impossible) — but v0.4.0 updates via the popup channel instead.** The v0.2.x approach (an **in-page** `fetch` of `version.json` from the ELSA document) was confirmed blocked — real-ELSA `securitypolicyviolation` testing showed `csp:true` for BOTH `connect-src` (v0.2.1) and `img-src` (v0.2.2). That whole feature was deleted in v0.3.0. **Do NOT re-add an in-page `fetch`/XHR/`<img>` phone-home from the ELSA document — that path is genuinely blocked.** v0.4.0's self-updating loader does its check in the **separate `window.open()` popup** (see the corrected bullet above), never from the ELSA page itself, which is why it works. The old v0.3.0 network-free weekly reminder (the `vwjb_upd_reminder_v1` Wednesday banner) still exists in the app as a fallback nudge.
- **Diagram capture only finds `<img>`** of sufficient size on numbered-overview pages. Inline SVG/canvas diagrams or cross-origin frames are not captured (diagnostic reports "diagrams kept: N").
- **Component numbering depends on the "+ ADD" button** text (English "ADD" / French "AJOUTER"). UI changes upstream could break it.
- **`detectTitle` (page header) is heuristic** — editable per page as the fallback. The diagnostic reports the detected header.
- **Cross-origin iframe content is unreadable** (browser security); paste-box is the fallback.
- **Re-scanning the same page can re-add a deleted item** (deletions persist but a fresh scan re-reads everything).
- **Repo + Pages are public** — the setup page URL is shareable but not access-restricted.
